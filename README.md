Lattice QCD in Rust.

## Introduction

Ruttice is a lattice QCD code written in Rust. Its idea is to use what Rust offers as far
as it goes to make the solvers and HMC fast, with the aim of simulations in pure Rust on
every kind of hardware.

It has Wilson, clover and Möbius domain-wall fermions, with a multigrid solver written for
each kind (Wilson-type and domain-wall) to compute two-point correlation functions quickly.
Gauge configurations are generated by HMC: pure gauge, two flavours, ratios of
determinants, and RHMC for single flavours.

The code is written for a clear structure (see [Architecture](#architecture)) and for
speed, at some cost in readability where the two pull apart: kernels are fused so that a
field is read and written as few times as possible, fields can be laid out in blocks of
sites for SIMD, and the low-level pieces (cache-bypassing stores, the layout of memory) are
written by hand.

**GPUs** are not supported yet. The plan is to run on them first through the CUDA core of
Bridge++, and to add a backend in Rust once CUDA is officially supported there, keeping
both.

What the code computes has been checked number by number against
[Bridge++](https://bridge.kek.jp/Lattice-code/) (see [Correctness](#correctness)).

## Quick start

You need a stable Rust toolchain and a gauge configuration.

```bash
git clone https://github.com/atsanroger/RutticeQCD.git
cd RutticeQCD
cargo build --release
```

This produces the program `target/release/ruttice`. It takes one argument, a parameter
file; paths inside the file are relative to the file itself.

Keep your own runs in `run/` at the top of the repository: git ignores that directory, so
configurations, parameter files and results can live there without ever being committed.
Copy an example into it, put the configuration next to it, and run:

```bash
mkdir -p run
cp examples/wilson_pion.yaml run/
cp /path/to/conf_04040408.txt run/
target/release/ruttice run/wilson_pion.yaml
```

The output for this example, on a 4×4×4×8 lattice:

```text
# lattice [4, 4, 4, 8] on cpu
# Wilson: κ = 0.12
# CG on Even_odd (the Schur complement on the even sites, CGNE), to |r|²/|b|² < 1e-28
# no preconditioner
# Local source at [0, 0, 0, 0], 1 columns per solve: meson correlators
# lattice    [4, 4, 4, 8]
# plaquette  0.625129946974942
# quark 1    40 iterations, 0 restarts, worst |D S - b|^2/|b|^2 = 8.835e-29, 0.119 s, peak memory 0.02 GB
# quarks channel t re im
11 PS 0 1.422503945020827e1 0.000000000000000e0
11 PS 1 6.530367660173256e-1 0.000000000000000e0
...
```

Lines starting with `#` describe the run. Every other line is one value of a correlator:
the two quarks it was built from (`11` is quark 1 with itself, `12` is quark 1 with quark
2), the channel, the time slice, and the real and imaginary parts.

For the kernels to use the SIMD registers of the machine, build for it:

```bash
RUSTFLAGS="-C target-cpu=native" cargo build --release
```

## Usage

### Parameter files

A parameter file has the sections and keys of a Bridge++ parameter file, in YAML (`.yaml`,
`.yml`) or TOML (`.toml`). Keywords (the values of choices) are read in any case and with or
without `_`: `BiCGStab`, `bicgstab` and `BICG_STAB` are the same. A key that does not exist
is an error when the file is read, with the alternatives; a key that is there but not used
by the run is named in a note.

The commented examples show every key:

| File | What it runs |
|---|---|
| [examples/wilson_pion.yaml](examples/wilson_pion.yaml) | Wilson fermions, point source, pion correlator |
| [examples/clover_two_flavours.yaml](examples/clover_two_flavours.yaml) | clover fermions, two quarks, smeared sources, every channel |
| [examples/clover_mg.yaml](examples/clover_mg.yaml) | clover fermions with the multigrid |
| [examples/mdwf_pv_eo_mg.yaml](examples/mdwf_pv_eo_mg.yaml) | Möbius domain-wall fermions with the multigrid (and `.toml`: the same in TOML, the multigrid from a file of its own) |
| [examples/hmc_domainwall_pv.yaml](examples/hmc_domainwall_pv.yaml) | HMC: two flavours of domain-wall fermions over Pauli-Villars, stout links |
| [examples/hmc_clover_rhmc_nf2p1.yaml](examples/hmc_clover_rhmc_nf2p1.yaml) | HMC: 2 + 1 flavours of clover fermions, the strange quark by RHMC |

The sections of a file that solves for propagators:

| Section | What it holds |
|---|---|
| `Main` | `lattice_size`; `grid_size` (processes per direction); `backend` (`cpu` or `simd`) and `simd_lanes` |
| `Gauge` | `config_filename_input` and `gauge_config_type_input` (`Text`, `ILDG`, `SciDAC`, `HDF5`) |
| `GaugeFixing` | optional: `gauge_fixing_type : Coulomb` and its parameters |
| `GaugeSmearing` | optional: stout or APE smearing of the links the fermions see |
| `Fopr` | the fermion: `fermion_type` (`Wilson`, `Clover`, `Mobius`) and its parameters |
| `Source` | `source_type` (`Local`, `Exponential`), `source_position` |
| `Quark_2` … `Quark_4` | Wilson and clover: further quarks, each a `Fopr` and a `Source` |
| `Solver` | `solver_type`, `operator_type`, the stopping rule, `preconditioner_type` |
| `MultiGrid` | the multigrid, used with `preconditioner_type : MG` |
| `Measure` | Wilson and clover: `channels` (`all`, or a list) |
| `Output` | Wilson and clover: `file`, to write the table to as well |

`Solver.operator_type` says where the system is solved, for the fine lattice and for the
coarse lattice of the multigrid alike: `Even_odd` (the default) solves the Schur complement
on the even sites, and the coarse system on the even coarse sites; `Lexical` solves on all
sites of both. Domain-wall fermions are always solved on the even sites
(`PV_right`, `PV_left`, `Normal_left` choose the form of the operator).

An HMC file has a format of its own for now (`lattice`, `start`, `hmc`, `actions`,
`output`; see the two examples). It will take the sections of Bridge++'s `HMC_General` in
the next version.

### Fermions and solvers

| Fermions | Solvers | Preconditioners |
|---|---|---|
| Wilson, clover | CG on the normal equations, BiCGStab, FGMRES; on all sites or on the even sites | multigrid (SAP or GMRES smoother) |
| Möbius domain-wall | GCR, BiCGStab, FGMRES on the Pauli-Villars preconditioned operator of the even sites; CG on its normal equations | multigrid (Chebyshev smoother), Chebyshev polynomial |

For every quark the propagator is computed for all twelve spin-colour components of the
source. Wilson and clover runs print the meson correlators of every pair of quarks (i, j)
with i ≤ j; domain-wall runs print the pion correlator and the residual mass.

The channels are named after the gamma matrices at the sink and at the source:

| Name | Sink ← source | Name | Sink ← source |
|---|---|---|---|
| `PS` | γ5 ← γ5 | `S` | 1 ← 1 |
| `V1` `V2` `V3` | γ_k ← γ_k | `G51` `G52` `G53` | γ5γ_k ← γ5γ_k |
| `A4_PS` | γ4γ5 ← γ5 | `S12` `S23` `S31` | iγ2γ1, iγ3γ2, iγ1γ3 at both ends |
| `PS_A4` | γ5 ← γ5γ4 | `A4_A4` | γ4γ5 ← γ5γ4 |

All but `A4_A4` were checked against Bridge++; `A4_A4` is not in Bridge++ and has no
reference values from another program.

### SIMD

With `backend : simd` the fields are kept in blocks of `simd_lanes` sites, and the operator
and the solvers work on whole blocks. In double precision 4 lanes fill a 256-bit register
(AVX2) and 8 a 512-bit one (AVX-512); the program must have been built for a processor that
has them (`target-cpu=native`, above), otherwise the blocks are computed with ordinary
instructions. The results are those of `cpu` up to the order of the sums in the solver. The
lattice is cut into that many equal parts by halving it, t first, then z, y, x; with
`Even_odd` the parts must have even extents, so a 4×4×4×8 lattice allows up to 8.

Whether blocks are faster depends on the machine: the kernels are limited by the memory
they move before they are limited by arithmetic.

### Several processes

The MPI version is a second program, `ruttice-mpi`, built when the feature `mpi` is turned
on. Building it needs an MPI installation (Open MPI, MPICH or Intel MPI) and libclang:

```bash
cargo build --release --features mpi
mpirun -np 4 target/release/ruttice-mpi run/wilson_pion.yaml
```

It reads the same parameter files and prints the same table. `Main.grid_size` is the number
of processes in x, y, z, t; the product must be the number of processes, and each number
must divide the lattice extent in its direction. Without it the lattice is split
automatically. With `Even_odd`, the part of the lattice on each process must have even
extents; with `simd`, it is that part that is cut into blocks.

`mpirun` must come from the same MPI installation the program was built with. If it does
not, every process believes it is alone, and the program stops with a message saying that
the process grid needs more processes than there are. After switching to another MPI
installation, run `cargo clean -p mpi-sys` before building again.

Every process reads the whole configuration file and keeps its part, so this is meant
for files that fit in memory. The results agree with a single process up to rounding.

### Generating configurations

`ruttice` given an HMC file runs trajectories and saves configurations. The actions: the
plaquette and rectangle (Iwasaki, …) gauge actions; two flavours of Wilson, clover or
domain-wall fermions, on all sites or on the even sites; their ratio to Pauli-Villars
fermions; and fractional powers of the determinant by a rational approximation (RHMC), with
the coefficients computed by the program. The links the fermions see can be stout smeared.
The integrator is leapfrog or Omelyan on several time scales; the force solves can start
from the solutions before them.

The momenta, the pseudofermions and the Metropolis test use the random numbers of
Bridge++, in its order, so a run of Bridge++'s `HMC_General` can be repeated number by
number.

### The gauge configuration file

| `gauge_config_type_input` | File |
|---|---|
| `Text` | plain text with one real number per line, the format Bridge++ calls `Text` |
| `ILDG` | the ILDG format: a LIME container with the records `ildg-format` and `ildg-binary-data` |
| `SciDAC` | a lattice-colour-matrix record written by the SciDAC QIO library: a LIME container with `scidac-binary-data` |
| `HDF5` | the dataset `gauge` of an HDF5 file, double precision, of shape `[Lt, Lz, Ly, Lx, 4, 3, 3, 2]`; needs a program built with `--features hdf5` and the HDF5 library |

All four keep the numbers in the same order, from the outermost loop to the innermost:

1. site, with x running fastest: `site = x + Lx * (y + Ly * (z + Lz * t))`
2. direction mu = x, y, z, t
3. the 3×3 link matrix row by row, real part then imaginary part of each entry

A file of the wrong length or for another lattice is rejected. The binary formats hold
big-endian reals in single or double precision; `ILDG` and `SciDAC` are read by the same
code, which accepts either kind of binary record and verifies the SciDAC checksum when the
file has one.

The LIME and HDF5 readers and writers were written from the descriptions of the formats and
have not yet been tried on files from other programs; the HDF5 layout is this program's own.

## Conventions

So that numbers can be compared with other codes:

- **Wilson operator.** `D ψ(x) = ψ(x) − κ Σ_μ [ (1 − γ_μ) U_μ(x) ψ(x+μ) + (1 + γ_μ) U_μ(x−μ)† ψ(x−μ) ]`.
  The hopping parameter is related to the bare mass by `κ = 1 / (2 m0 + 8)`.
- **Clover operator.** `D = D_Wilson − κ c_SW Σ_{μ<ν} F_μν γ_μ γ_ν`, with the clover-leaf
  field strength `F_μν = (Q − Q†)/8`, Q being the sum of the four plaquettes in the μ-ν
  plane that start at x.
- **Möbius domain-wall operator.** `D = 1 + Y + W (b − c Y)`, W the Wilson operator with
  mass −M5 and Y the hop in the fifth dimension with the quark mass in its corners, in the
  normalisation of Bridge++'s `Fopr_Domainwall`; b = 1, c = 0 is Shamir's operator.
- **Gamma matrices.** Dirac representation (γ4 diagonal), Hermitian, with
  γ5 = [[0, 1], [1, 0]] in 2×2 blocks.
- **Boundary conditions** apply to the fermions only; the gauge field is always periodic.
- **Meson correlator.** `C(t) = Σ_x Tr[ (γ5 Γ_sink) S1(x,t) (Γ_source γ5) S2(x,t)† ]`,
  where S1 and S2 are the propagators of the two quarks from the same source and the trace
  is over spin and colour. No further sign or normalisation is applied.
- **Plaquette.** Normalised so that a unit gauge field gives 1.
- **Coulomb gauge.** Maximises Σ_x Σ_i Re tr U_i(x) over the spatial directions i on every
  time slice. The violation of a time slice is Σ_x |Δ(x)|² / (4 Nc V_t), where Δ(x) is the
  traceless part of M − M† with M = Σ_i [U_i(x−i) − U_i(x)], |·|² sums the squares of all
  real components and V_t is the number of sites in a time slice.

These follow Bridge++, which is what the results are checked against.

## Correctness

Two kinds of checks run with `cargo test`.

**Checks that need nothing else.** Properties the result must have whatever the numbers
are: gauge covariance, the free-field result for a plane wave, D† being the adjoint of D,
the solution of a linear system satisfying it when put back, the same answer from every
solver and every layout of the fields, the same bits for any number of threads, forces
being the derivatives of their actions.

**Comparisons with Bridge++.** The plaquette; the Wilson, clover and domain-wall operators
applied to a vector; solver iteration counts; meson correlators in thirteen channels on
every time slice, for one and two quark flavours and for point and smeared sources, with
and without Coulomb gauge fixing; the domain-wall pion correlator; and one trajectory of
each of Bridge++'s HMC tests (quenched, Wilson, clover, domain-wall, RHMC, even-odd). The
comparisons of the solves are written down in [docs/COMPARISON.md](docs/COMPARISON.md).

The comparisons read a Bridge++ test configuration, `conf_04040408.txt`, that ships with
Bridge++ and is not part of this repository. Put it in `run/` and `cargo test` finds it;
or keep it elsewhere and name the directory:

```bash
RUTTICE_BRIDGE_TESTS=/path/to/that/directory cargo test
```

**Without the file those comparisons print `SKIPPED` and count as passed**, and the rest
still run: to know that the comparisons ran, look for `SKIPPED` in the output of
`cargo test -- --nocapture`.

## Architecture

One Cargo package, `ruttice`.

| Directory | Contents |
|---|---|
| `src/` | the library, one directory per subject (below) |
| `apps/` | the programs: `ruttice`, `ruttice-bench`, and with the feature `mpi` `ruttice-mpi`, `ruttice-bench-mpi` and `ruttice-mpi-check` |
| `tests/` | the checks described above, one file per subject; `tests/data/` holds reference values |
| `examples/` | the parameter-file examples, `pion.rs` (the library used directly), and programs that time kernels (`*_bench.rs`, `hmc_eo_measure.rs`) |
| `docs/` | `COMPARISON.md` |

| Directory under `src/` | Contents |
|---|---|
| `field` | fields, storage types, the vector and linear-operator interfaces |
| `lattice` | lattice geometry, neighbour tables, even-odd decomposition, loops over sites in parallel |
| `comm` | communication between processes |
| `backend` | backends that need an external library: the communicator on MPI (feature `mpi`) |
| `kernel` | arithmetic on single sites: complex numbers, colour matrices, spinors, gamma matrices, SIMD lanes |
| `numerics` | small dense linear algebra; rational approximations |
| `io` | reading and writing gauge configurations |
| `gauge` | plaquette, field strength, gauge fixing, smearing, products of links along paths |
| `fermion` | the Wilson, clover and Möbius domain-wall operators; even-odd preconditioning |
| `solver` | Krylov solvers, mixed precision, and under `preconditioner` the polynomial preconditioners and the multigrids |
| `hmc` | actions and their forces, integrators |
| `measure` | sources and meson correlators |
| `app` | parameter files, building what they name, running and reporting |

Files with the same role have the same name. Under `fermion`, each fermion has

| File | Role |
|---|---|
| `mod.rs` | the operator, its parameters, what it is |
| `site.rs` | the part that acts within a site (the clover term; the fifth dimension) |
| `lexical.rs` | the operator on all sites, in lexical order |
| `even_odd.rs` | its even-odd blocks and the operators made of them |

and what only it has: `wilson/` the sweep of the hopping term (`sweep*.rs`), which the other
two are built on; `mdwf/quark_4d.rs` the four-dimensional quark fields of five-dimensional
ones. Clover fermions are the Wilson operator with another site term, so `clover/` has only
`mod.rs` and `site.rs`. The multigrids are named the same way
(`multigrid/wilson.rs`, `mdwf_even_odd.rs`, `mdwf_lexical.rs`), and so are the actions of
HMC (`hmc/gauge_action.rs`, `fermion_action.rs`, `even_odd.rs`, `rational.rs`).

A field is `Field<T, Kind, Sites, Layout>`: the storage type (`f32`, `f64`), what it holds
(`Gauge`, `Spinor`, `Coarse`), which sites (`Lexical`: all of them in lexical order;
`Half`: those of one parity) and how they are laid out (`Aos`: site by site; `Aosoa<W>`:
blocks of W sites, one per SIMD lane). The solvers know only vectors and linear maps;
nothing outside `solver::preconditioner::multigrid` knows about fermions.

### Using it as a library

The program is a thin layer over the library; anything it does can be done from Rust code.
The shortest complete example is [examples/pion.rs](examples/pion.rs). Its core:

```rust
let lat = Lattice::single_node([4, 4, 4, 8]);
let u = read_bridge_text(&path, &lat)?;

let mut op = Wilson::<f64>::new(&lat, WilsonParams { kappa, boundary });
op.set_gauge(&u)?;

let b = point_source::<f64>(&lat, [0, 0, 0, 0]);   // twelve right-hand sides
let mut s = b.zeros_like();
solve_even_odd(&op, index, &mut s, &b, |schur, x_e, rhs| {
    solve_cgne(&mut Cg::new(stop), schur, x_e, rhs)
})?;

let c = pion_correlator(&s);                        // one value per time slice
```

## Status and plans

Version 0.1.0. See [CHANGELOG.md](CHANGELOG.md).

Not there yet:

- GPUs (see the introduction)
- HMC files in the sections of Bridge++
- the multigrids on lattices larger than 16⁴: they have been developed and measured on 12⁴
  and 16⁴, where a multigrid has little to gain; what they save on physical volumes is not
  known yet
- Landau gauge fixing; baryons

The repository holds programs that time the kernels (`ruttice-bench`,
`examples/*_bench.rs`), not timings: those depend on the machine.
